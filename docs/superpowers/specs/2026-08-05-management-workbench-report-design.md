# CRM 管理层工作台与经营复盘报告设计

## 1. 背景

真实产品已经具备浏览器本地 Excel 导入、字段识别、确定性规则分析、项目聚合、筛选、人工复核、Excel 明细导出和 Markdown 摘要导出。现有业务引擎可以继续使用，但工作区信息组织和报告表达存在两类问题：

- 工作区将总览、问题清单和复盘摘要平铺为三个页签，分析、处理和输出之间的职责不够清楚。
- Markdown 报告按“总体结论、优先关注事项、重点部门与负责人、规则分布摘要、建议行动”分段，内容主要是指标和规则的再次罗列，缺少具体项目、客观证据、管理决策和责任动作之间的连续叙事。

本设计将 Refero 风格概念页中已确认的信息层级和预览交互迁移到真实 React 产品，但不迁移概念页的模拟数据、模拟事业部切换或模拟导入历史。真实产品的 Excel 和规则分析能力保持唯一业务基础。

## 2. 产品定位与第一读者

产品继续定位为浏览器本地运行的 **CRM 储备项目分析与经营复盘工具**，不是完整 CRM、项目管理系统或整改任务系统。

Markdown 报告的第一阅读对象是事业部负责人和管理层。CRM 运营人员负责导入、筛选和复核，但最终输出必须让管理者不查看系统规则或原始 Excel，也能回答以下问题：

1. 本期发生了什么。
2. 哪些风险或异常值得管理层关注。
3. 哪些具体项目需要决策。
4. 谁需要完成什么动作。
5. 结论依据是什么。

## 3. 设计原则

### 3.1 业务引擎不重写

保留现有 Excel 解析、字段映射、金额换算、规则识别、筛选、项目聚合、本地复核和导出逻辑。界面重组不能改变规则命中数量、项目金额、筛选结果或复核记录的含义。

### 3.2 状态只有一个来源

`ReviewTool` 继续持有真实分析、筛选和复核状态。“问题项目”和“人工复核”读取同一个项目集合和同一份 `ReviewRecordMap`，并通过同一个 `onChangeReview` 更新。不得在两个页面各自复制复核状态。

### 3.3 规则负责事实，业务人员负责结论

- 客观证据只能来自导入数据和确定性规则。
- 真实原因、继续推进与否及处理结论只能来自人工复核记录。
- 没有人工复核时，报告必须显示“待业务确认”，不得推断销售行为、客户意图或项目停滞原因。
- 建议动作可以根据已确认事实和预设业务口径生成，但必须标记为建议，不能冒充已下达任务。

### 3.4 管理正文与核查附录分层

正文围绕经营结论、管理决策、重点项目和责任动作组织；规则分布、筛选口径和完整明细放入附录。管理者先理解业务，再按需核查数据来源。

### 3.5 预览与下载同源

报告预览和 Markdown 下载必须使用同一份不可变字符串快照。页面不能分别拼装两份近似内容。

## 4. 范围

### 4.1 本期包含

- 保留原产品落地页和“开始分析”入口。
- 重组分析完成后的工作区导航和页面职责。
- 新增独立“人工复核”视图，但复用现有复核状态和控件。
- 将现有管理摘要重构为管理决策报告。
- 增加右侧报告预览栏和预览后下载流程。
- 保留邮件反馈、复制邮箱、代码与版本入口。
- 保留 Markdown 报告和项目明细 Excel 两种导出。
- 增加必要的单元、组件、集成和浏览器回归验证。

### 4.2 本期不包含

- 后端、账号、云端存储或多人协作。
- CRM API、CRM 写回或原始 Excel 上传服务器。
- 通知、任务分配、整改截止日期或进度催办。
- 大模型 API 或 AI 自动判定业务原因。
- 概念页中的模拟四事业部选择、模拟导入历史或模拟项目数据。
- 与本次工作区和报告无关的业务规则重构。

## 5. 工作区信息架构

落地页保持不变。用户完成真实 Excel 导入和必要确认后进入工作区。

### 5.1 左侧数据控制区

继续承载真实文件、工作表、识别结果和分析参数。它回答“当前分析的数据从哪里来、采用什么口径”，不承担业务结果导航。

### 5.2 工作区导航

导航按使用阶段分组：

- **分析**
  - 数据总览
  - 问题项目
- **处理**
  - 人工复核
- **输出**
  - 复盘报告

分组标题解释阶段，导航项解释具体任务。导航项前不添加无语义的特殊字符；选中状态使用背景、文字和边框区分。数量徽标只用于“问题项目”和“人工复核”等真实计数。

### 5.3 数据总览

承担范围判断和优先级判断，继续使用当前筛选后的 `AnalysisResult`：

- 项目总数和储备金额。
- 客观问题项目数和需要人工复核项目数。
- 部门或负责人金额分布。
- 问题和经营观察分布。

金额使用自适应单位：不足 1 亿元时优先显示万元，达到 1 亿元后显示亿元；图表标题和数值使用同一口径。

### 5.4 问题项目

展示当前筛选范围内的完整项目级发现，包括客观事实、人工判断和经营观察。保留搜索、筛选、分页、选择导出、完整证据和关联项目能力。

### 5.5 人工复核

只展示存在 `manualFindings` 的项目，并复用问题项目中现有的状态、说明和历史记录逻辑。每个项目以稳定 `rowKey` 关联复核记录，切换项目时必须从该项目的记录重新读取表单值，避免结论串到其他项目。

保存后应立即同步到：

- 当前项目的复核状态和历史记录。
- 人工复核待处理数量。
- 数据总览中的复核统计。
- 当前筛选范围对应的报告数据。

复核区不新增第二份草稿存储。若使用局部表单草稿，项目键变化时必须初始化为新项目值，保存时只更新当前项目键。

### 5.6 复盘报告

页面先展示管理层摘要和当前报告状态，而不是直接下载：

- 当前分析范围。
- 本期核心结论。
- 待决策事项数量。
- 待业务确认项目数量及涉及金额。
- “预览完整报告”主操作。
- “导出项目明细 Excel”独立操作。

Markdown 下载入口放在预览栏中。用户先检查内容，再下载当前预览快照。

## 6. 管理层报告结构

报告标题为“储备项目经营复盘报告”，并显示事业部或筛选范围、分析日期、数据来源和统计口径。

### 6.1 一、本期经营结论

用不超过四条结论回答：

- 分析项目数量和储备总额。
- 存在客观问题的项目数量及涉及金额。
- 待业务确认的项目数量及涉及金额。
- 最集中的经营问题及本期最需要推动的管理动作。

结论必须由聚合数据得到，不使用空泛表述。金额同时提供适合阅读的单位和明确数值。

### 6.2 二、需要管理层决策的事项

事项从当前筛选范围内的项目级发现生成，不再只列规则标签。每项包含：

- 项目名称和项目编码。
- 储备金额、当前阶段、部门和负责人。
- 客观证据。
- 已填写的业务复核结论；没有时显示“待业务确认”。
- 需要管理层决定的问题。
- 基于现有口径生成的建议动作。

排序采用可解释的固定规则：先显示“确认业务风险”，再显示“待复核”，同一状态下按金额从高到低，其后按项目编码或稳定项目键排序。不得创建不透明的 AI 风险评分。

正文最多显示 10 个重点项目。其余符合条件的项目在附录中列出，并提示剩余数量。

### 6.3 三、重点项目处理清单

使用 Markdown 标准表格呈现，字段固定为：

| 项目 | 金额 | 当前阶段 | 发现的问题 | 人工复核结论 | 建议动作 | 责任部门 / 负责人 |
|---|---:|---|---|---|---|---|

为保证可读性，每个单元格使用短文本。完整规则原因和关联项目仍由项目明细 Excel 承载。未填写项目编码、阶段、部门、负责人或复核说明时必须显示明确缺失状态，不得静默省略。

### 6.4 四、部门责任与后续安排

按部门聚合需要处理的重点项目，展示：

- 待处理项目数量。
- 涉及储备金额。
- 主要问题。
- 建议完成的动作。
- 已完成复核数量和待复核数量。

当前产品没有任务系统，因此不生成虚假的截止日期、已指派状态或完成进度。报告中的“责任部门 / 负责人”来自 Excel 数据，“建议动作”用于管理层安排，不代表系统已经通知责任人。

### 6.5 五、附录：数据范围与识别规则

附录包含：

- 文件或工作表范围的非敏感描述。
- 当前筛选条件。
- 项目数量、金额口径和分析日期。
- 各规则类别和复核状态的数量分布。
- 未进入正文的其余待确认项目。
- 报告边界声明。

附录明确说明：本报告基于导入数据、确定性规则和浏览器本地人工复核记录生成，真实原因和最终处理决定由业务人员确认。

## 7. 报告数据模型

重构 `ReviewSummaryData`，使展示组件和 Markdown 生成器消费同一份管理层报告模型。建议模型由以下独立单元组成：

- `meta`：标题、生成日期、分析范围、免责声明。
- `executiveConclusions`：固定上限的经营结论。
- `decisionItems`：项目级管理决策事项。
- `priorityProjects`：正文最多 10 个项目的处理清单。
- `departmentActions`：部门级责任和建议动作汇总。
- `appendix`：口径、规则分布、复核分布和剩余项目。

构建流程为：

1. 从当前筛选后的 `AnalysisResult` 聚合项目级发现。
2. 通过项目 `rowKey` 关联唯一 `ReviewRecordMap`。
3. 计算问题项目数量、金额、部门聚合和复核状态。
4. 使用固定排序规则选择正文项目。
5. 生成结构化管理报告模型。
6. 由该模型生成安全 Markdown 字符串。
7. 预览组件安全解析并呈现同一 Markdown 字符串快照。

所有用户输入继续经过 Markdown 行内转义。预览不得使用未经净化的 `dangerouslySetInnerHTML`。

## 8. 预览、快照与下载交互

### 8.1 打开预览

点击“预览完整报告”时，同时捕获：

- 完整 Markdown 字符串。
- 建议文件名。
- 生成时间。
- 当前筛选签名和复核数据版本。

这些值组成不可变的 `ReportPreviewSnapshot`。抽屉打开期间不重新计算其正文。

### 8.2 数据变化提示

预览打开后，如果筛选或复核记录发生变化，保留当前正文并显示“数据已更新，请重新生成预览”。用户可以：

- 继续下载当前看到的旧快照。
- 点击“重新生成预览”替换为最新快照。

不得静默改变已经阅读中的报告。

### 8.3 下载

“下载 Markdown”只下载当前 `ReportPreviewSnapshot.markdown`。按钮显示短暂“已下载”反馈。Excel 明细导出继续使用当前工作区筛选结果，不与 Markdown 快照合并。

### 8.4 抽屉行为

- 桌面端从右侧进入，宽度受视口约束。
- 窄屏占满可用页面并独立滚动。
- 支持关闭按钮、抽屉底部关闭、可见遮罩点击和 `Escape`。
- 打开后焦点进入抽屉，关闭后返回“预览完整报告”按钮。
- 背景内容设置为不可交互状态，避免键盘焦点落入遮罩后方。
- 遮罩渐显约 160ms，抽屉进入约 220ms。
- 遵循 `prefers-reduced-motion`。

## 9. 组件边界

为减少回归，采用组件级迁移，不整体替换工作台：

- `ReviewTool`：继续持有真实导入、分析、筛选和复核状态。
- `AnalysisWorkspace`：只负责分组导航和当前视图切换。
- `AnalysisOverview`：继续显示当前筛选后的总览。
- `ProjectIssueList`：继续承担完整问题项目清单；通过受控展示参数复用于人工复核视图，不复制复核业务逻辑。
- `ReviewSummary`：改为管理层摘要入口，不再同时承担完整报告正文。
- `ReportPreviewDrawer`：只负责快照展示、重新生成、下载、焦点和关闭行为。
- `domain/report`：负责结构化报告模型、固定排序、限制数量、安全 Markdown 和快照输入，不依赖浏览器 DOM。

若复用 `ProjectIssueList` 会产生大量条件分支，应抽取共享的单项目复核控件，而不是把两个完整页面复制一份。

## 10. 错误与空状态

- 无分析数据时不能打开报告预览，并引导先导入 Excel。
- 当前筛选无项目时显示“当前筛选范围没有项目”，不生成全量报告替代。
- 无规则发现时仍生成经营结论，并明确“本期未识别到需要关注的客观线索”。
- 有规则发现但无人工作结论时显示“待业务确认”，不得省略该项目。
- 金额无法解析时显示“金额待确认”，不得按 0 元参与金额排序。
- 下载失败时保留预览并显示可重试错误，不关闭抽屉。
- 本地复核存储读取失败时沿用现有容错，不删除或覆盖原存储内容。

## 11. 测试与回归控制

### 11.1 实施顺序

1. 重组工作区导航，不改领域数据。
2. 增加人工复核视图，复用现有 `ReviewRecordMap`。
3. 先以测试定义管理层报告模型，再替换旧报告结构。
4. 增加报告预览快照和安全渲染。
5. 最后统一工作区样式和克制动效。

每一步完成后运行相关测试；任何既有能力回归时先修正，再进入下一步。

### 11.2 自动化测试

领域测试至少覆盖：

- 总体数量和金额计算。
- 客观问题、待复核和确认业务风险的区分。
- 项目与复核记录按 `rowKey` 独立关联。
- 管理决策项目排序和正文最多 10 项。
- 未解析金额、缺失部门、缺失负责人和缺失复核说明。
- Markdown 注入转义和表格字符转义。
- 预览快照与下载字符串完全一致。
- 筛选或复核变化后的“报告已过期”判断。

组件测试至少覆盖：

- 四个工作区导航项及真实数量徽标。
- 问题项目和人工复核共用状态，切换项目不串值。
- 保存复核后统计和报告数据更新。
- 预览前不直接下载 Markdown。
- 抽屉四种关闭方式、焦点返回和背景不可交互。
- 数据变化后提示重新生成。
- 邮件反馈、复制邮箱、代码与版本入口仍存在。
- 窄屏布局和减少动态效果设置。

### 11.3 端到端人工验证

使用真实脱敏 Excel 完成以下完整链路：

1. 从保留的落地页进入工具。
2. 导入 Excel，完成字段和工作表确认。
3. 切换部门、负责人、金额和问题筛选。
4. 查看总览与完整问题证据。
5. 依次复核至少两个不同项目，填写不同结论并来回切换确认不串值。
6. 确认保存后的数量、历史记录和报告同步变化。
7. 生成报告预览，核对五部分管理内容。
8. 修改复核记录，确认旧预览不变且出现更新提示。
9. 重新生成并下载 Markdown，逐字比对预览快照。
10. 导出项目明细 Excel。
11. 验证反馈入口、键盘操作、桌面和移动端布局。

### 11.4 完成门槛

- 当前基线的 230 项测试全部保持通过。
- 新增测试全部通过。
- 生产构建通过；现有构建体积警告不作为本需求新增失败，但不能显著扩大产物。
- 真实脱敏 Excel 完整链路通过。
- 桌面和移动端截图无文本重叠、截断、空白按钮或不可点击控件。
- 不修改、不删除用户当前未跟踪文件。

## 12. 验收标准

1. 原落地页、真实 Excel 导入、字段识别、筛选、规则证据、分页、复核、Excel 导出和反馈入口全部保留。
2. 工作区清楚区分分析、处理和输出，用户能理解每个板块要完成的事情。
3. 两个不同项目的复核状态和说明互不污染，保存后使用同一数据源同步到统计和报告。
4. 管理层报告形成“经营结论 → 决策事项 → 重点项目 → 部门动作 → 数据附录”的连续叙事。
5. 报告正文列出具体项目、金额、客观证据、人工结论、建议动作和责任范围，不再只罗列规则名称。
6. 未经人工确认的真实原因明确标记为待确认，系统不代替业务人员做最终判断。
7. 正文最多显示 10 个重点项目，其余内容进入附录或 Excel 明细。
8. 报告预览与下载 Markdown 使用同一快照，数据变化不会静默修改当前预览。

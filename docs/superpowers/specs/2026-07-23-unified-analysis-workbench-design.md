# CRM 销售运营分析工作台设计

## 1. 背景

当前工具已经能够读取任意 CRM 导出的 Excel，自动识别字段和业务口径，并用固定规则发现数据质量问题、维护风险和经营观察。使用 150 条模拟数据后，暴露出三个主要问题：

- 同一个项目可能在多个结果区域重复出现，负责人需要反复上下翻找。
- 每个项目的审查控件过多，运营人员处理 300–400 个项目时会产生大量无必要点击。
- 复盘 Markdown 将大量项目明细全部写入正文，报告过长，不适合管理者快速阅读。

本设计将产品重新明确为轻量的 **CRM 销售运营分析与复盘工具**。它负责发现、组织和解释分析结果，不负责通知、任务分配、整改进度或 CRM 数据写回。

## 2. 目标

### 2.1 产品目标

1. 一个项目在结果页中只出现一次，并集中展示该项目的全部分析结果。
2. 让负责人直接看到触发问题的日期、超期天数和关联项目，不需要再回 Excel 查证。
3. 让客观规则自动进入分析结果，只把模糊判断留给人工。
4. 让运营人员能够通过部门、销售经理和问题标签快速缩小分析范围。
5. 无论分析 150 条还是 400 条数据，页面都保持可扫描、可分页和可导出。
6. 将管理摘要与项目明细分开，生成短而可读的 Markdown 报告。

### 2.2 非目标

本阶段不实现：

- CRM API 接入、后端服务或数据写回。
- 销售人员账号、任务分配、通知发送或整改截止日期。
- “已通知、待整改”等流程状态。
- 大模型 API、AI 自动判定业务事实或 AI 自动修改源数据。
- 把浏览器里的 UI 样式原样导出到 Markdown。

这些能力可以作为未来独立产品阶段评估，不能混入当前轻量分析工具。

## 3. 用户与使用场景

### 3.1 销售负责人

通常只关注本部门或本人项目。通过部门、销售经理筛选后，查看项目问题清单和少量人工核验项。

### 3.2 销售运营人员

负责全公司的月度或周期性 Excel 分析，数据规模可能达到 300–400 个项目。重点是快速识别整体问题、定位优先范围、导出明细，而不是逐条维护流程状态。

## 4. 核心设计原则

### 4.1 项目是唯一展示单位

结果页以项目为行单位。一个项目触发多个规则时，所有标签、原因、日期证据和关联项目都集中在同一行，不再按规则分类拆成多个纵向区域。

### 4.2 分析结论与人工判断分开

系统根据规则可以确定的事实直接展示，不要求用户逐条确认。只有存在业务歧义的结果才显示人工判断控件。

### 4.3 筛选和导出优先于流程跟踪

复选框只用于选择项目并导出当前清单，不代表任务状态，也不记录通知或整改进度。CRM 仍然是业务事实和修改动作的唯一来源。

### 4.4 信息分层而不是信息堆叠

页面、摘要和明细分别承担不同职责：页面负责交互分析，摘要负责管理层快速阅读，Excel 明细负责完整数据查看。

## 5. 信息架构

分析完成后进入一个三页签工作区：

### 5.1 分析总览

展示固定数量的核心指标和结构分布：

- 项目总数
- 储备金额
- 客观问题项目数
- 需要人工判断项目数
- 经营观察项目数
- 部门和销售经理储备金额分布
- 问题标签数量分布

总览只承担范围判断和优先级判断，不展开全部项目明细。

### 5.2 项目问题清单

默认按优先级和项目编码稳定排序，每页 50 条，可切换页码。提供以下全局筛选：

- 搜索项目名称、客户名称或项目编码
- 部门
- 销售经理
- 问题标签
- 金额区间
- 项目状态
- 只看需要人工判断
- 审查状态（仅针对存在人工判断的项目）

清单列固定为：

1. 选择
2. 项目摘要
3. 部门 / 负责人
4. 关键日期
5. 全部分析结果
6. 人工判断

项目摘要只显示项目名称、项目编码、客户名称和金额，不重复在项目名称前拼接客户名称。

### 5.3 复盘摘要

展示固定长度的管理摘要，并提供两个导出动作：

- 下载复盘摘要 Markdown
- 导出项目明细 Excel

摘要正文不包含所有项目逐条明细，项目级证据通过项目问题清单或独立 Excel 查看。

## 6. 项目级结果模型

### 6.1 分组规则

现有分析结果先通过稳定的项目键分组，再渲染到项目清单。优先使用项目编码；没有项目编码时使用源数据行键和规范化项目名称组合，避免不同记录意外合并。

### 6.2 项目行内容

每行项目必须能够在不打开其他区域的情况下看到：

- 项目名称
- 项目编码
- 客户名称
- 部门和销售经理
- 储备金额和金额单位
- 最近跟进日期
- 预计签约日期
- 规则标签、问题原因和严重程度
- 需要人工判断的控件（如有）

### 6.3 日期证据

日期类结果必须同时展示原始日期和计算结果：

- 跟进超期：显示最近跟进日期和“超过 X 天”。
- 签约日期超期：显示预计签约日期和“距分析日已过 X 天”。
- 日期逻辑异常：显示创建日期、最近跟进日期或预计签约日期的对比关系。

用户不需要为了理解标签再回到 Excel 查询日期。

### 6.4 关联项目

重复记录、疑似重复立项、疑似撞单和名称相似结果必须在同一项目行内显示关联项目：

- 关联项目编码
- 关联项目名称
- 关联客户
- 关联销售经理
- 关联关系类型

关联项目不再另起一条孤立结果；同一关系的两端项目都保留关联信息，方便负责人从任一项目查看完整关系。

## 7. 规则结果的三种显示层级

### 7.1 客观事实：自动进入分析

这类结果不显示逐项目审查下拉框：

- 跟进超过 30 天
- 预计签约日期早于分析日期
- 日期早于创建日期等确定性日期逻辑异常
- 缺少字段、日期格式错误、金额无效
- 金额分档和重点金额提示

用户可以通过筛选和导出处理这些结果，但不需要逐条点击“确认”。

### 7.2 模糊问题：保留人工判断

这类结果保留轻量人工判断：

- 疑似重复记录
- 疑似重复立项
- 疑似撞单
- 名称相似
- 疑似占位金额

保留现有的“待复核、确认数据错误、确认业务风险、已忽略”语义，但只在确实存在业务歧义的项目行显示。当前阶段不新增“已通知、待整改”等流程状态。

### 7.3 经营观察：只展示不要求处理

这类结果不显示审查控件：

- 重点项目金额分档
- 长周期储备
- 询价类项目
- 低概率和经营结构分布

它们用于复盘和管理观察，不代表系统认定存在错误或风险。

## 8. 复盘摘要 Markdown

### 8.1 固定结构

Markdown 使用纯文本、标题、列表和标准表格，不包含浏览器 UI 卡片、颜色、页签或侧边栏。固定结构为：

1. 分析范围和总体结论
2. 优先关注事项
3. 重点部门与负责人
4. 规则分布摘要
5. 三条以内建议行动

### 8.2 长度限制

无论项目数量如何增加，摘要只展示固定数量的重点内容：

- 最多 3 条管理结论
- 最多 4 类重点问题
- 最多 5 个部门或负责人范围
- 最多 3 条建议行动

项目明细不拼接到摘要正文；需要完整列表时使用项目问题清单或导出的 Excel。

### 8.3 报告边界

报告由本地确定性规则生成，不调用大模型。报告中的“建议行动”只能引用规则发现的事实和预设业务口径，不得推断未在数据中出现的客户意图或销售行为。

## 9. 本地数据与状态边界

- Excel 原始数据继续只在当前浏览器中读取和分析。
- CRM 仍是正式数据源，工具不写回 CRM。
- 人工判断记录只保存在浏览器本地，用于本次分析和复盘稿同步。
- 重新上传 CRM 导出的新文件仍然是验证整改结果的方式，不设计独立的整改任务流。

## 10. 验收标准

### 10.1 功能验收

- 150 条和 400 条项目都只产生一份项目级清单，不再按五类结果重复出现。
- 同一项目的多个标签、原因、日期证据和关联项目在同一行可见。
- 跟进日期、预计签约日期和超期天数无需查 Excel 即可理解。
- 重复立项和撞单两端项目互相显示关联信息。
- 只有模糊问题显示人工判断控件，客观事实和经营观察不要求逐条确认。
- 部门和销售经理筛选同步影响指标、清单、摘要和导出范围。
- 项目问题清单分页，每页默认 50 条。
- Markdown 摘要长度不随项目总数线性增长，并可单独导出项目明细 Excel。

### 10.2 边界验收

- 页面没有通知、任务、负责人分派、整改截止日期或 CRM 写回入口。
- 不接入大模型 API、后端服务或 CRM API。
- 规则结论仍然可解释、可追溯，模糊问题仍由业务人员确认。

### 10.3 测试验收

- 单元测试覆盖项目分组、关联项目、日期证据和三类显示层级。
- 组件测试覆盖筛选、分页、人工判断控件显示条件和项目摘要字段。
- 导出测试覆盖摘要 Markdown 的固定结构与明细 Excel 的当前筛选范围。
- 浏览器验证 150 条模拟数据，检查桌面和移动端的表格滚动、页签、筛选和导出按钮。

## 11. 后续阶段边界

只有在有真实企业持续使用、明确的流程协作需求和数据合规要求后，才另行设计“CRM 连接与整改协作系统”。该阶段应拥有独立的产品目标、权限模型、后端架构和数据安全评审，不作为本设计的隐式延伸。

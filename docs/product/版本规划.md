# Git 版本规划

## 当前基线

- 当前产品基线：`v0.8.0`
- 基线日期：2026-08-09
- 发布分支：`main`
- 产品边界：浏览器本地处理 Excel，固定规则负责识别问题，人工负责确认业务事实和最终结论。

`V0.1` 至 `V0.7` 的已完成能力见项目根目录的 `CHANGELOG.md`。`V0.8` 汇总此前未编号的统一分析工作台、项目明细导出、管理复盘报告、预览快照和界面一致性工作。

## 后续方向

| 版本 | 状态 | 范围 |
| --- | --- | --- |
| `v0.8.0` | 已实现 | 当前浏览器本地规则分析、人工复核和报告导出基线 |
| `v0.9.0` | 规划中 | DeepSeek AI 分析报告；规则结果仍是事实依据，AI 负责解释和建议 |
| 未编号 | 构想 | AI 多维图表、销售跟进记录分析和下一步动作建议 |

规划中的能力不代表已经开发、测试或部署。确认设计并完成当前代码验证后，才能进入对应版本的已实现记录。

## 版本规则

- 产品阶段使用 `0.x.0`：例如新增一条完整可用的 AI 分析链路，从 `0.8.0` 升为 `0.9.0`。
- 修复版本使用 `0.x.y`：不改变产品边界的缺陷修复，从 `0.8.0` 升为 `0.8.1`。
- Git 标签使用带 `v` 的语义版本号，例如 `v0.8.0`。
- 每个版本只在测试和生产构建通过后创建标签。
- GitHub 推送和 Cloudflare Pages 部署是两项独立操作，必须分别验证和记录。

## 发布检查

1. 更新 `CHANGELOG.md`、`package.json` 和 `package-lock.json`。
2. 运行当前源码测试、TypeScript 检查和生产构建。
3. 创建独立版本提交。
4. 在版本提交上创建 annotated tag。
5. 单独确认是否推送 GitHub。
6. 单独部署并验证 Cloudflare Pages，不能用 GitHub 已更新代替部署证据。
